# Генерация карточек из фида

HTTP API для списка карточек, поиска по артикулу и генерации из JSON описано в [README-api.md](README-api.md).

Скрипт `feed_card.py` читает YML/XML-фид 3sta.ru, выбирает товар, скачивает его первое фото и собирает JPG в существующем фирменном шаблоне. По умолчанию выбран компактный профиль: 900×1200, JPEG quality 82, 4:2:0, progressive/optimize. Его можно задать явно: `--jpeg-quality 82 --max-edge 1200 --jpeg-subsampling 2`, либо через переменные `CARD_JPEG_QUALITY`, `CARD_MAX_EDGE`, `CARD_JPEG_SUBSAMPLING`. Уменьшение разрешения и повторное JPEG-сжатие имеют потери; гарантий «максимально сжать совсем без потерь» нет. API генеративных изображений и ключи не нужны: используется настоящее фото товара и готовые фоны проекта.

## Запуск

Откройте терминал в папке проекта. Python 3.10+:

```powershell
pip install -r requirements.txt
python feed_card.py --id S207352
```

ID — значение атрибута `id` у `<offer>` в фиде. По умолчанию адрес фида уже задан: https://3sta.ru/yandex/feed.xml.

```powershell
# Первый товар
python feed_card.py
# Первые 10 товаров, только тёмная карточка
python feed_card.py --limit 10 --theme dark
# Первые 10 товаров, обе темы в отдельных папках
python feed_card.py --limit 10 --theme all
# Другой фид или локальный XML
python feed_card.py --feed "https://example.com/feed.xml" --id PRODUCT123
python feed_card.py --feed "feed.xml" --limit 10
# Весь фид — только при явном указании 0
python feed_card.py --limit 0
```

Карточки сохраняются в две папки: `feed-output/dark/<артикул>.jpg` и `feed-output/light/<артикул>.jpg`, например `dark/S207352.jpg`. Артикул берётся из `id` товара в фиде. При `--theme dark` заполняется только тёмная папка; для обеих тем используйте `--theme all` (по умолчанию). Исходное фото `source.img` и все данные `product.json` хранятся отдельно, в соседней папке `feed-output-sources/<артикул>/`. Для другой папки добавьте `--output "D:/cards"` — исходники будут в `D:/cards-sources/`. Повторный запуск перезаписывает JPG этого товара. Старые PNG не удаляются и не обновляются: их ссылки продолжают работать. Карточки, созданные ранее в старой структуре папок, автоматически не перемещаются.

## Сжатие уже готовых PNG без повторной загрузки фида

Для сжатия **уже существующих JPG на месте**, оценки 180 тысяч файлов, продолжения после остановки и серверных команд см. [COMPRESSION.md](COMPRESSION.md). Старый `convert_cards.py` ниже только создаёт копии PNG → JPG и сам по себе не освобождает место оригиналов.

```bash
python convert_cards.py --output feed-output --theme all
```

На сервере: `sudo -H -u productcard /opt/product-card/.venv/bin/python /opt/product-card/convert_cards.py --output /opt/product-card/feed-output --theme all`.

Команда создаёт JPG рядом с PNG, сохраняет размер изображения и не меняет параметры или исходники. Уже существующие JPG пропускаются. При обновлённом API они автоматически получают приоритет перед PNG. PNG остаются на диске, поэтому конвертация уменьшает размер передаваемых изображений, но не освобождает место: для новых JPG требуется дополнительное свободное место. Не запускайте конвертацию одновременно с генерацией тех же карточек. Качество JPEG задано в `card_output.py`.

На карточке отображаются бренд, модель, размер, диаметр, индексы нагрузки и скорости, сезон. **Все** поля товара, атрибуты и параметры с единицами сохраняются в `product.json`, включая цену, ссылки, шипы и RunFlat. Они не помещаются на основной макет. Если после извлечения данных нет обязательных характеристик (бренда, модели, размера, диаметра, индекса нагрузки или скорости), артикула или фото, товар пропускается до скачивания и создания файлов. В логе появляется `SKIP <артикул>: Missing required data: ...` с перечнем недостающих полей. Пустые строки, пробелы и `null` также считаются отсутствующими данными. Сезон необязателен; скрипт не придумывает характеристики. Модель берётся из `model`, а при отсутствии — из названия без бренда и размера.

Перед генерацией HTTP/HTTPS-фид полностью скачивается во временный файл и проверяется до конца как XML. При обрыве загрузки, несовпадении `Content-Length` или повреждённом XML выполняется до 5 попыток с паузами 2, 4, 8 и 16 секунд. Число попыток можно задать через `--feed-attempts 5`, сетевой тайм-аут — через `--timeout 30`. До сообщения `Feed ready: ...; XML validated` товары не генерируются. Временный файл удаляется после завершения обработки или обычной ошибки; он занимает место на диске, а XML не хранится целиком в памяти. Локальный XML также проверяется полностью, но не скачивается и не повторяется.

После проверки XML товары читаются из локального файла потоком; извлечение прекращается после выбранного товара или лимита. Поэтому даже `--limit 1` теперь требует загрузки и проверки всего фида. `--limit` считает просмотренные товары, включая пропущенные, а не число созданных карточек. Относительные ссылки на фото по-прежнему разрешаются относительно исходного адреса фида, не временного файла. Поиск ID ближе к концу потребует прочитать предыдущие товары. Неполные товары пропускаются, обработка продолжается; сами пропуски не приводят к коду ошибки. Ошибка скачивания или генерации отдельного товара записывается как `ERROR`, после неё обработка остальных также продолжается, но итоговый код завершения будет `1`. Если все попытки загрузки фида исчерпаны или локальный XML повреждён, запуск завершается с кодом `1` до генерации карточек.

В конце выводится `Summary: processed=N, generated=N, skipped=N, failed=N`: просмотрено товаров, полностью обработано товаров (все выбранные темы), пропущено из-за неполных данных и завершилось с ошибкой. Даже если все товары пропущены, при отсутствии других ошибок код завершения — `0`; проверяйте счётчики в логе.

Локальная проверка без сети и реальной генерации: `python -m unittest test_sizes test_compression test_feed test_api -v`. Тестовые файлы и тестовый workflow исключены из Git по запросу владельца; в серверном клоне эта команда недоступна.

Шрифты выбираются автоматически: Arial на Windows или DejaVu Sans на Linux; можно положить DejaVuSans.ttf и DejaVuSans-Bold.ttf в `assets/fonts`. Удаление фона рассчитано на фото с белым однородным фоном. Нестандартное фото или длинное название может потребовать проверки готовой карточки.

Светлая кайма очищается в узкой полосе вдоль края товара с сохранением полупрозрачности. Если фон фото слегка серый и остаётся видимым, попробуйте `--threshold 225` (по умолчанию `235`). Меньший порог удаляет больше светлого фона; на фото со светлыми деталями товара снижайте его осторожно.

## Как изменить оформление

Метрические размеры с дефисом вместо `R` поддерживаются в фиде и API: `255/85-16`, `255/85 - 16 LT`. На карточке отображаются `255/85-` и плашка `16` (либо `16LT`); дефис не заменяется на `R`. Название модели очищается от такого размера, индексы извлекаются отдельно. Старый формат `255/85 R16` продолжает работать.

Также поддерживаются размеры `5.5R13C` (на карточке `5.5` и плашка `R13C`) и `28x8.5R15` (`28x8.5` и `R15`). Десятичная запятая нормализуется в точку; профиль и единицы не пересчитываются. Разбор одинаков для фида и API.

Размеры `33х10.5-15`, `33x10.5-15 LT`, `33×10,5 R15 TL`, `225/75 R16TL` и `195 R14LT` поддерживаются в фиде и API. Дюймовый размер выводится как `33x10.5-` обычным текстом и `15` (или `15LT`) в жёлтой плашке: дефис остаётся в размере, не заменяется на `R`. Внутренний формат параметров не меняется. Размер из строки «Размер» приоритетнее раздельных параметров ширины/профиля/диаметра; это не позволяет смешать дюймовые значения с метрическими. Суффикс TL/LT сохраняется, в том числе если присутствует только в параметре диаметра. Индексы по-прежнему обязательны.

Размеры без указанного профиля, например `195R14` и `195 R14`, поддерживаются парсером и API: на карточке выводятся `195` и плашка `R14`. Профиль не подставляется. Поддерживается суффикс `C`: `195/75 R16C` и `195 R14C`; он сохраняется на плашке диаметра. Размер и индексы удаляются из названия модели; двойной индекс нагрузки, например `106/104`, сохраняется.

Светлая тема использует `assets/light-paint-background-v8.png`: более чистые широкие фиолетовые и лаймовые мазки без мелких брызг. Тёмный фон не изменён. Старый светлый фон сохранён в `assets/paint-background-v4.png`; его можно выбрать явно: `--background assets/paint-background-v4.png`. Новый фон применяется при следующей генерации, уже сохранённые карточки автоматически не меняются.

Два примера из локальных исходников сохранены в `preview-output/light-v8/`: `S058436.png` (двойной индекс нагрузки `104/102`) и `S058617.png`.

Все шины по умолчанию проходят единый пресет: мягкое выравнивание яркости и контраста и повышение резкости внутри силуэта. Обработка выполняется после масштабирования; маска защищает края, прозрачность сохраняется. Параметры заданы в `finish_tyre()` файла `build.py`. Пресет делает фото более похожими по тону, но не исправляет различия в ракурсе, освещении или исходном разрешении. Для отключения добавьте `--raw-photo` к команде запуска.

Макет задаётся в функции `compose()` файла `banner_card.py` и применяется к обеим темам. Вызовы `text()` задают координаты `(x, y)`, текст, размер шрифта и цвет; `maxwidth` ограничивает ширину и автоматически уменьшает шрифт. Цвета тем заданы переменными `bg`, `fg`, `secondary`, акцентные цвета — `LIME` и `PURPLE`. Фон можно заменить через `--background` и `--dark-background`.

Размер и диаметр расположены рядом: `225/65` обычным текстом, только `R18` на жёлтой плашке. Положение плашки автоматически рассчитывается по ширине размера, зазор — `24` пикселя. Текст начинается на высоте `418`, начальный размер шрифта — `128`; при необходимости оба значения уменьшаются вместе до общей ширины `1068`. После изменения макета запустите скрипт повторно, чтобы пересобрать карточки.
